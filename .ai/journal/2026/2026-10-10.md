## Planned: multi-event R2 bucket, live/archive pipeline split

Discussed and wrote up a plan for moving off the single-event, flat-bucket (`cc5`) pipeline to a
new `cdawgva` bucket holding every event under a per-event key prefix, with the fetch concept split
into a recurring live pipeline and a one-shot archive pipeline. Full write-up:
`.ai/tasks/active/multi-event-r2-bucket-live-archive-split.md`. Nothing implemented yet.

Key decisions made during discussion:

- Event storage keys use a canonical key we define (`cyclethon-1`..`cyclethon-5`), not Tiltify's
  real campaign slug, since the real slugs for events 1-4 don't follow a `cyclethon-N` pattern and a
  future non-cyclethon event wouldn't have one at all.
- `CURRENT_LIVE_EVENT_KEY` is nullable. As of today, Cyclethon 5 has already ended (event window was
  2026-04-05 to 2026-04-19 JST), so there is currently no live event, and the pointer should be
  `null` rather than pointing at a finished event.
- Archive output includes `latest-100`/`latest-500` slices too, for output-shape consistency with
  the live pipeline, even though nothing polls a finished event live.
- Confirmed the operator's understanding of `refresh.yml`: its real recurring trigger is
  cron-job.org calling the `workflow_dispatch` endpoint externally, not GitHub's own `on.schedule`
  cron (which is vestigial in the current file).
- No new GitHub Actions workflow for archiving. Archiving runs locally with `DATA_STORE=r2`.
- `bin/backup-r2.sh` is dropped entirely rather than updated.

Process note: on the first pass I wrote this plan to `docs/tasks.md`, which does not match this
